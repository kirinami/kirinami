# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`@kirinami/create-app` — a scaffolding CLI (`kirinami-create-app`) that copies a project template into a target
directory. The entire program is `main.js` (~250 lines, ESM, Node >= 22.22); everything else under `templates/` is
inert payload that is never executed here, only copied.

The git repo is the `kirinami/kirinami` monorepo, but `packages/create-app` is currently its only package.

## Working on the CLI

```bash
node main.js my-app --template react-ssr   # scaffold into ./my-app
node main.js                               # interactive: framework -> variant prompts
```

Adding or renaming a template requires two coordinated edits: the directory under `templates/`, and the `FRAMEWORKS`
array in `main.js` (`TEMPLATES`, the `--template`/`-t` allowlist, is derived from its variants). A template directory
that is not listed in `FRAMEWORKS` is unreachable.

Scaffolding copies every file byte-for-byte with one exception: `package.json` is parsed and re-emitted with `name`
replaced by the prompted package name. Nothing else is templated — no placeholder substitution exists.

### The `_gitignore` convention

This package's own `.gitignore` (and `.npmignore`, a byte-identical copy) ignores by glob across all subdirectories:
`**/.gitignore*`, `**/.env*` (except `.env.example`), `**/yarn.lock*`, `**/package-lock.json*`, `**/node_modules/**`,
`**/.build/**`, `**/.yarn/**` (except `releases/`, `plugins/`, etc.).

So a template cannot ship a real `.gitignore`: it is stored as `_gitignore` and renamed at scaffold time by the
`renameFiles` map in `main.js`. When adding files to a template, check them against those globs first — a file matching
one is silently absent from both the commit and the published npm tarball. (`react-spa` currently ships no `_gitignore`
at all, so projects scaffolded from it start without one.)

## The templates

Each template is a standalone project, not a workspace member — `cd templates/<name>`, then `npm install` before
running anything. No lockfiles are committed.

| Template | dev | build / start | lint | test |
| --- | --- | --- | --- | --- |
| `nest-graphql`, `nest-restapi` | `npm run dev` (:3000) | `npm run build` → `.build/`, `npm start` | `npm run lint` | `npm test`, `npm run test:e2e` |
| `react-ssr` | `npm run dev` (:5173) | `npm run build` → `.build/`, `npm start` | `npm run lint` | `npm test` |
| `react-spa` | `npm run dev` | `npm run build`, `npm run preview` | `npm run lint` | — |

A single test: `npx vitest run src/lib/react/server/escape.test.ts`, or `npx vitest run -t 'name'`. The Nest templates
split unit tests (`src/**/*.{test,spec}.ts`, `vitest.config.mjs`) from e2e (`test/**/*.e2e-{test,spec}.ts`,
`vitest.config.e2e.mjs`); both configs pass with no tests, so a green run may mean nothing ran.

`lint` runs `tsc --noEmit` and then `eslint --fix` — it mutates files. The Nest `lint`/`test` scripts also run
`prisma generate` first, which needs `.env` (copy from `.env.example`); `dev` runs `prisma migrate dev`, so Postgres
must be up (`docker compose up postgres`).

### Nest templates (`nest-graphql`, `nest-restapi`)

The two are near-identical skeletons over Fastify + Prisma; `restapi` swaps resolvers for controllers plus
`@nestjs/swagger`, and carries both `*.dto.ts` (HTTP) and `*.input.ts` files. Changes to shared concerns (auth,
`common/`, prisma schema, execution-context helpers) usually belong in both.

- Feature modules follow `src/<feature>/{services,resolvers|controllers,dto,models}/`, wired in `app.module.ts`.
- `PrismaService` extends `PrismaClient` and additionally exposes `$drizzle` — `prisma/schema.prisma` runs a
  `drizzle-prisma-generator` alongside the Prisma client, emitting `prisma/drizzle/schema.ts`. Both query paths exist.
- Auth is the `BearerAccess(roles?)` decorator → `BearerGuard` → `auth/utils/execution-context.ts`, whose helpers are
  the one place that normalizes HTTP, GraphQL and graphql-ws requests into a single request object. Anything that
  reaches for `context.switchToHttp()` directly will break under subscriptions.
- `src/metadata.ts` is generated by the Nest GraphQL CLI plugin (configured in `nest-cli.json`) — do not hand-edit.
- Builds go to `.build/server`, `public/` is copied to `.build/public`, and `start` runs `prisma migrate deploy` first.

### `react-ssr`

The most intricate template — a hand-rolled SSR stack, not a framework.

- **One Fastify app for both modes.** `src/main.ts` builds the server (API routes, static files, catch-all SSR route).
  In production it is the built `.build/server/main.js`. In dev there is no separate server process: the inline
  `fastify-dev-server` plugin in `vite.config.js` `ssrLoadModule`s `src/main.ts` per request and hands it Vite's
  request/response, then injects Vite's client scripts and dev CSS into `</head>` via a stream transform
  (`src/lib/vite.ts` walks the module graph to extract styles). Vite's `environments.ssr`/`environments.client` produce
  `.build/server` and `.build/public`; the server reads `.vite/manifest.json` to resolve asset URLs.
- **`Document.tsx` owns `<html>`**, and the client calls `hydrateRoot(document, ...)`. `entry.server.tsx` and
  `entry.client.tsx` must build structurally identical provider trees, or hydration breaks — edit them as a pair.
- **Two-pass prefetch.** `lib/react/server/prefetchRender.ts` + `RenderPromises.ts` render, collect pending react-query
  queries, await them, and re-render until the tree is stable. Queries opt out via `meta.ssr === false`, `enabled:
  false`, or `suspense: true` (see the `onCollect` predicate in `entry.server.tsx`).
- **Hydration handoff** is four `window.__static*HydrationData` globals (assets, i18n, query cache, app store), written
  through `escapeJson` in `bootstrapScriptContent` and typed in `src/globals.d.ts`.
- **Per-request state**: `createQueryClient()`, `createI18n()` and `createAppStore()` are factories called once per
  request and passed through providers — never module-level singletons.
- Routing is `:language`-prefixed (`src/routes.tsx`); an unprefixed path redirects to `DEFAULT_LANGUAGE`. The API lives
  in-process under `/api/*` (`src/features/todos/api.ts`, Fastify + zod type provider).

### `react-spa`

A plain Vite + React 19 + React Router SPA. Deliberately minimal: no server, Docker, husky, tests, or `.env`.

## Conventions shared by the templates

- `@/*` → `src/*` in every template, but resolved differently per tool: `react-ssr` via `resolve.tsconfigPaths`,
  `react-spa` and the Nest vitest configs via an explicit alias that duplicates the tsconfig path.
- Prettier: `printWidth: 120`, `singleQuote`, `trailingComma: 'all'`.
- ESLint flat config, typed linting, with a custom `simple-import-sort` group order (side-effect imports, node
  builtins, packages, `@/…`, relative, then `*.module.scss`). Running `npm run lint` is the way to get it right rather
  than sorting by hand.
- `@typescript-eslint/consistent-type-definitions: ['error', 'type']` — use `type`, not `interface` (the few
  `interface` declarations exist only for module augmentation and carry an eslint-disable).
- No default `react` import (`no-restricted-imports`); named imports only.
